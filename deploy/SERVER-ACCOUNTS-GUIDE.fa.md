# راهنمای رفع ورود و ثبت‌نام و مدیریت حساب‌های T4V روی Docker

## یافته‌های تأییدشده از گزارش سرور

تنظیمات فعال سرور کاربر شامل سرویس‌های `db` و `web` است؛ دستورهای بخش‌های بعد که از `app` و `migrate` استفاده می‌کنند، مخصوص Compose همین مخزن‌اند و پیش از هماهنگ‌کردن فایل‌های استقرار نباید عیناً روی تنظیمات فعلی اجرا شوند.

گزارش سرور سه مشکل مشخص نشان داد:

- PostgreSQL رمز اتصال کاربر `t4v` را رد می‌کند (`P1000` و `28P01`). ابتدا رمز واقعی همین نقش باید با رمز موجود در `DATABASE_URL` سرویس `web` هماهنگ شود. تغییر متغیر `POSTGRES_PASSWORD` به‌تنهایی کافی نیست.
- دستور فهرست جدول‌ها در پایگاه دادهٔ انتخاب‌شده با `POSTGRES_DB` هیچ رابطهٔ قابل‌مشاهده‌ای پیدا نکرد. پس بعد از اتصال صحیح باید نام پایگاه داده و اعمال migration بررسی شود؛ این خروجی به‌تنهایی وجودنداشتن همهٔ داده‌ها در کل سرور را ثابت نمی‌کند.
- کانتینر قدیمی migration به علت نبودن `/app/node_modules/.bin/prisma` اجرا نشده است. اصلاح رمز به‌تنهایی این مشکل را رفع نمی‌کند؛ migration باید از تصویر دارای Prisma CLI اجرا شود. برای تعیین دستور سازگار با سرور، Dockerfile فعال نیز باید بررسی شود.

ابتدا از پایگاه دادهٔ فعلی پشتیبان بگیرید، سپس در `docker compose exec db psql -U t4v -d postgres` دستور `\password t4v` را اجرا و رمز اتصال سرویس `web` را وارد کنید. رمز واقعی را در چت نفرستید. پس از آن سلامت اتصال را بررسی کنید؛ برای مشکل نبودن جدول‌ها مرحلهٔ migration همچنان لازم است.

## نتیجهٔ بررسی سایت

در بررسی زندهٔ این نوبت، `https://t4v.ir/api/health` پاسخ ۵۰۳ و `database: unavailable` داد. ثبت‌نام پاسخ خطای ساختاریافته می‌دهد، اما ورود هنوز پاسخ خالی با وضعیت ۵۰۰ دارد. اصلاح مسیر ورود هم در نسخهٔ جدید پروژه انجام شده است و باید روی سرور منتشر شود.

این نتیجه، خرابی ارتباط برنامه با PostgreSQL را تأیید می‌کند؛ تشخیص اینکه رمز اشتباه است، سرویس خاموش است، یا آدرس نادرست است، به اجرای بررسی زیر روی سرور نیاز دارد. هیچ حساب یا رمز تولیدی روی سرور شما از این محیط تغییر داده نشده است.

## حساب‌ها چه تفاوتی دارند؟

| حساب | محل استفاده | روش تنظیم |
|---|---|---|
| کاربر سیستم‌عامل سرور | اتصال SSH و اجرای Docker | توسط مدیر سرور؛ در فرم ورود سایت وارد نمی‌شود |
| کاربر PostgreSQL | اتصال برنامه به پایگاه داده | `POSTGRES_USER` و `POSTGRES_PASSWORD` و `DATABASE_URL` در `.env` |
| مدیر اصلی PostgreSQL | ایجاد پایگاه داده و نقش‌ها | فقط کار نگهداری؛ رمز آن رمز مدیر سایت نیست |
| مدیر وب‌سایت | ورود به `/admin` و مدیریت کامل سایت | دستور ساخت مدیر در این راهنما؛ رمز به‌صورت هش در `admin_accounts` ذخیره می‌شود |
| کاربر عادی سایت | ورود و ثبت‌نام با ایمیل | فرم ثبت‌نام یا بخش کاربران پنل مدیر؛ در جدول `users` ذخیره می‌شود |

ساخت کاربر عادی سایت به ساخت کاربر جدید PostgreSQL نیاز ندارد. حساب محلی مدیر و کاربران محلی هم خودکار به پایگاه دادهٔ سرور منتقل نمی‌شوند.

## ۱. آماده‌سازی بدون حذف اطلاعات

برای نصب کاملاً تازه، `bash deploy/install.sh t4v.ir` پایگاه داده، جدول‌ها و مدیر نام‌دار `admin` را آماده می‌کند و مشخصات مدیر را در فایل خصوصی ذخیره می‌کند. برای سایت فعلی ابتدا مراحل تشخیص زیر را انجام دهید؛ نصب دوباره جایگزین تشخیص خطای اتصال نیست.

از طریق SSH وارد پوشهٔ پروژه روی سرور شوید. دستورهای زیر در همان پوشه اجرا می‌شوند. ابتدا نسخهٔ جدید همین پروژه را روی سرور قرار دهید؛ فایل `.env` موجود و داده‌های Docker را حفظ کنید.

این دستورها برای Docker Compose همین مخزن هستند. اگر نام سرویس‌ها یا فایل‌های Compose را تغییر داده‌اید، نام‌های واقعی را جایگزین کنید.

```bash
docker compose -f docker-compose.yml -f docker-compose.production.yml ps -a
```

پیش از تغییر رمز، مجوزها یا انتشار، از پایگاه داده نسخهٔ پشتیبان بگیرید:

```bash
mkdir -p backups
chmod 700 backups
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backups/before-auth-repair.dump
chmod 600 backups/before-auth-repair.dump
test -s backups/before-auth-repair.dump
```

اگر پشتیبان‌گیری خطا داد، فایل خروجی را پشتیبان معتبر فرض نکنید. قبل از تغییرات، اتصال را بررسی کنید. از `docker compose down -v` یا پاک‌کردن volume استفاده نکنید؛ این کار اطلاعات کاربران را حذف می‌کند.

## ۲. محل واردکردن نام کاربری و رمز پایگاه داده

فایل `.env` در ریشهٔ پروژه روی سرور قرار دارد. این فایل را فقط روی سرور ویرایش کنید؛ در چت یا مخزن عمومی قرار ندهید.

```dotenv
POSTGRES_USER=t4v
POSTGRES_PASSWORD=YOUR_EXISTING_DATABASE_PASSWORD
POSTGRES_DB=t4v
DATABASE_URL=postgresql://t4v:YOUR_EXISTING_DATABASE_PASSWORD@db:5432/t4v?schema=public
APP_DOMAIN=t4v.ir
PUBLIC_SHORT_URL_BASE=https://t4v.ir
COOKIE_SECURE=true
APP_PORT=3000
APP_SECRET=KEEP_EXISTING_APP_SECRET
DASHBOARD_SECRET=KEEP_EXISTING_DASHBOARD_SECRET
PAYMENT_ENCRYPTION_KEY=KEEP_EXISTING_PAYMENT_ENCRYPTION_KEY
```

این نمونه شامل رمز واقعی نیست؛ عبارت‌های انگلیسی بالا را عیناً در تنظیمات فعال نگذارید. مقادیر موجود کلیدهای برنامه و پرداخت را حفظ کنید. تغییر کلید رمزنگاری پرداخت می‌تواند اطلاعات اتصال درگاه‌های ذخیره‌شده را غیرقابل‌خواندن کند.

در Compose این پروژه، نام میزبان پایگاه داده **`db`** و پورت داخلی آن **`5432`** است. `localhost` داخل کانتینر برنامه به خود برنامه اشاره می‌کند. آدرس محلی توسعه با پورت `55432` نباید به سرور کپی شود.

اگر رمز شامل `@`، `#`، `%`، `/` یا نویسه‌های ویژه است، در بخش رمزِ `DATABASE_URL` باید URL-encode شود؛ خود `POSTGRES_PASSWORD` همان رمز اصلی است. برای نصب تازه، رمز تصادفی hex تولیدشده توسط نصب‌کننده این مشکل را ندارد.

**نکتهٔ مهم برای نصب موجود:** تغییر `POSTGRES_PASSWORD` در `.env` رمز کاربر موجود در volume PostgreSQL را عوض نمی‌کند. این متغیر فقط هنگام ایجاد اولیهٔ داده‌های PostgreSQL استفاده می‌شود. ناهماهنگی رمز موجود و فایل `.env` یکی از علت‌های محتمل این خطاست؛ هنوز بدون گزارش سرور تأیید نشده است.

```bash
chmod 600 .env
```

## ۳. بررسی دقیق اتصال، جدول‌ها و مجوزها

ابزار بررسی فقط اطلاعات عمومی اتصال را چاپ می‌کند؛ رمز، نشانی کامل اتصال و اطلاعات کاربران چاپ نمی‌شوند. این ابزار اطلاعاتی را تغییر نمی‌دهد. ابتدا تصویر نگهداری نسخهٔ جدید را بسازید:

```bash
docker compose build migrate
docker compose up -d db
docker compose run --rm --no-deps migrate node scripts/diagnose-database.mjs
```

| خروجی بررسی | اقدام |
|---|---|
| `ECONNREFUSED` | سرویس `db`، پورت داخلی و شبکهٔ Compose را بررسی کنید |
| `ENOTFOUND` | نام میزبان باید در شبکهٔ کانتینر قابل شناسایی باشد؛ در این پروژه `db` است |
| `28P01` | نام کاربری یا رمز واقعی PostgreSQL با `DATABASE_URL` هم‌خوان نیست |
| `3D000` | نام پایگاه داده اشتباه است یا پایگاه داده هنوز ساخته نشده |
| `42501` | کاربر پایگاه داده مجوز لازم برای جدول‌های برنامه را ندارد |
| `SCHEMA_MISSING` یا `MIGRATIONS_PENDING` | ابتدا پایگاه دادهٔ صحیح را تأیید کنید و سپس migration اجرا کنید |
| همهٔ موارد `PASS` | اتصال و ساختار پایگاه داده سالم است؛ برنامهٔ در حال اجرا را با تنظیمات جدید بازسازی کنید |

اگر ابزار هنوز اجرا نمی‌شود، گزارش سرویس‌ها را روی خود سرور ببینید:

```bash
docker compose logs --tail=100 db app migrate
```

برای ارسال گزارش، رمزها، رشته‌های اتصال و اطلاعات شخصی را حذف کنید. خروجی `docker compose config` ممکن است همهٔ رمزها را نشان دهد؛ آن را منتشر نکنید.

### اصلاح رمز موجود، فقط در صورت تأیید خطای 28P01

ابتدا نام کاربر واقعی پایگاه داده را تأیید کنید. در نمونهٔ زیر نام آن `t4v` است:

```bash
docker compose exec db psql -U t4v -d postgres
```

در محیط PostgreSQL:

```text
\password t4v
\q
```

دستور اول رمز جدید را دوبار به‌صورت مخفی می‌پرسد. همین رمز را در `POSTGRES_PASSWORD` و با encoding مناسب در `DATABASE_URL` وارد کنید. اگر سرویس‌های دیگری از این نقش استفاده می‌کنند، تنظیمات آن‌ها هم باید هماهنگ شود. اگر اتصال با `t4v` ممکن نیست یا نقش وجود ندارد، نام کاربر اولیهٔ volume را از مدیر سرور بگیرید؛ با حذف volume مشکل را حل نکنید.

## ۴. اعمال ساختار پایگاه داده و انتشار اصلاحات

پس از سالم‌شدن اتصال:

```bash
docker compose build app worker migrate
docker compose run --rm migrate
docker compose -f docker-compose.yml -f docker-compose.production.yml up -d --force-recreate app worker caddy
docker compose run --rm --no-deps migrate node scripts/diagnose-database.mjs
curl -fsS https://t4v.ir/api/health
```

انتظار داریم پاسخ سلامت شامل `status: ok` و `database: connected` باشد. اجرای `prisma migrate deploy` اطلاعات را reset نمی‌کند؛ در صورت خطا ادامه ندهید و گزارش migration را بررسی کنید. برای بررسی جزئی‌تر:

```bash
docker compose run --rm migrate npx prisma migrate status
```

## ۵. ساخت مدیر وب‌سایت با دسترسی کامل

پس از اتصال صحیح و اجرای migration:

```bash
mkdir -p .local
chmod 700 .local
docker compose run --rm --no-deps \
  -e PUBLIC_SHORT_URL_BASE=https://t4v.ir \
  -v "$PWD/.local:/app/.local" \
  migrate node scripts/create-admin.mjs admin
```

ابزار مدیر `admin` را با رمز تصادفی قوی ایجاد می‌کند. مشخصات ورود در فایل خصوصی `.local/admin-admin.json` ذخیره می‌شود. آن را فقط روی سرور بخوانید:

```bash
sudo cat .local/admin-admin.json
```

سپس به `https://t4v.ir/admin` بروید و نام کاربری و رمز همین فایل را وارد کنید. حسابی با این نام اگر از قبل وجود داشته باشد، ابزار رمز آن را تغییر نمی‌دهد. رمز داخل فایل را در چت نفرستید. فایل را در password manager شخصی نگهداری کنید؛ آن را به پوشهٔ عمومی سایت منتقل نکنید.

### اگر می‌خواهید رمز دلخواه وارد کنید

یک فایل خصوصی `.env.admin` بسازید که فقط این خط را داشته باشد:

```dotenv
T4V_ADMIN_PASSWORD=YOUR_STRONG_NEW_ADMIN_PASSWORD
```

رمز باید ۸ تا ۱۲۸ نویسه باشد؛ بهتر است طولانی و مستقل از رمز پایگاه داده انتخاب شود. سپس برای ایجاد **مدیر جدید**:

```bash
chmod 600 .env.admin
docker compose run --rm --no-deps \
  -e PUBLIC_SHORT_URL_BASE=https://t4v.ir \
  -v "$PWD/.env.admin:/app/.env.admin:ro" \
  -v "$PWD/.local:/app/.local" \
  migrate node --env-file=.env.admin scripts/create-admin.mjs site_admin
```

این ابزار بازیابی یا تغییر رمز حساب موجود نیست. اگر رمز مدیر قبلی گم شده، با دسترسی سرور یک مدیر جدید با نام متفاوت بسازید، وارد شوید و حساب قبلی را از بخش مدیران مدیریت کنید.

`DASHBOARD_SECRET` مربوط به ورود اولیهٔ قدیمی است. بعد از ایجاد مدیر نام‌دار، برای ورود از نام کاربری و رمز همان حساب استفاده کنید.

## ۶. ایجاد کاربر عادی و آزمون نهایی

بعد از ورود مدیر، در بخش کاربران، ایمیل، رمز و اعتبار اولیه را وارد کنید. کاربر عادی هم می‌تواند در صفحهٔ ثبت‌نام حساب بسازد. برای هر کاربر سایت، نقش PostgreSQL نسازید.

موارد زیر را روی سرور بررسی کنید:

1. سلامت پایگاه داده `connected` است.
2. ثبت‌نام با ایمیل آزمایشی جدید موفق است و داشبورد باز می‌شود.
3. پس از خروج، ورود با همان ایمیل و رمز موفق است.
4. مدیر می‌تواند یک کاربر آزمایشی ایجاد کند و کاربر با مشخصاتش وارد شود.
5. پس از راه‌اندازی مجدد کانتینر برنامه، ورود همچنان موفق است.

حساب آزمایشی را پس از بررسی از پنل مدیر حذف کنید. در نسخهٔ جدید، خطاهای ورود و ثبت‌نام با پاسخ JSON و شناسهٔ پیگیری مدیریت می‌شوند؛ این اصلاح جایگزین بازیابی اتصال پایگاه داده نیست.

## ۷. ساخت نقش و پایگاه دادهٔ اختصاصی تازه، در صورت نیاز

برای نصب تازه با Compose استاندارد، سرویس PostgreSQL کاربر و پایگاه داده را از `.env` می‌سازد؛ اجرای این بخش لازم نیست. برای پایگاه دادهٔ موجود سایت هم این بخش را اجرا نکنید.

نقش `POSTGRES_USER` در تصویر استاندارد PostgreSQL نقش مدیر اولیهٔ پایگاه داده است. ابزار اختصاصی زیر نقش کم‌اختیارتر می‌سازد؛ تغییر نقشِ پایگاه دادهٔ موجود نیازمند بررسی مالکیت جدول‌ها و برنامهٔ انتقال جداگانه است و در این راهنما خودکار انجام نمی‌شود.

ابزار `scripts/setup-database.mjs` برای PostgreSQL دیگری که دسترسی مدیریتی آن را دارید آماده شده است. نقش جدید، غیر-superuser است و فقط مالک پایگاه دادهٔ اختصاصی جدید می‌شود. ابزار نقش یا پایگاه دادهٔ موجود را تغییر نمی‌دهد و در صورت وجود نام‌ها متوقف می‌شود.

فایل خصوصی `.env.database-admin`:

```dotenv
DATABASE_ADMIN_URL=postgresql://DATABASE_ADMIN:ENCODED_ADMIN_PASSWORD@DATABASE_HOST:5432/postgres
APP_DB_USER=t4v_app
APP_DB_NAME=t4v_new
# اختیاری؛ در صورت حذف، رمز تصادفی تولید می‌شود
APP_DB_PASSWORD=YOUR_STRONG_NEW_DATABASE_PASSWORD
```

با Node.js 22 یا جدیدتر و وابستگی‌های پروژه:

```bash
chmod 600 .env.database-admin
node --env-file=.env.database-admin scripts/setup-database.mjs
```

آدرس اتصال جدید در `.local/database.env` ذخیره می‌شود. مقدار آن را در محیط برنامه تنظیم کنید و migration را اجرا کنید. رمز مدیر PostgreSQL را به برنامه ندهید. این عملیات حساب‌ها و اطلاعات پایگاه دادهٔ قبلی را به پایگاه دادهٔ جدید منتقل نمی‌کند.

## فایل‌های حساس

`.env`، `.env.admin`، `.env.database-admin`، پوشهٔ `.local` و نسخه‌های پشتیبان حاوی اطلاعات حساس‌اند. فایل آموزشی فعلی هیچ رمز واقعی ندارد و قابل اشتراک است؛ فایل‌های حساس را همراه آن ارسال نکنید.
