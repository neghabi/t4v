# راهنمای پروندهٔ کاربران، احراز هویت و نظارت بر لینک‌ها

## رفتار نسخهٔ جدید

- ثبت‌نام به نام کامل، موبایل، نوع فعالیت، شرح محتوای موردنظر و رضایت به بررسی اطلاعات نیاز دارد. کسب‌وکار و سازمان باید نام مجموعه را هم وارد کنند.
- کاربر از «پرونده و احراز هویت» در داشبورد، ایمیل و موبایل را تأیید می‌کند و سپس مدارک خصوصی را بارگذاری می‌کند.
- مدیر از فهرست کاربران وارد پرونده می‌شود: اطلاعات، مدارک، وضعیت تماس‌ها، خریدهای واقعی، نوع بسته‌های اعتبار، سطح تخصیص‌یافتهٔ حساب، لینک‌های کاربر و سابقهٔ تصمیم‌ها نمایش داده می‌شود.
- سطح استاندارد/تجاری/سازمانی فعلاً تخصیص مدیریتی است؛ معادل خرید اشتراک نیست. خرید واقعی با سفارش‌های پرداخت‌شده و بستهٔ اعتبار تفکیک می‌شود. این نسخه محدودیت تجاری جدید یا فروش اشتراک تازه‌ای ایجاد نمی‌کند.
- مدیر ابتدا مدرک هویتی و برای فعالیت غیرشخصی، مدرک کسب‌وکار را بررسی می‌کند. سپس می‌تواند پرونده را تأیید کند. ایمیل یا موبایل از طریق دکمهٔ مدیر به‌طور صوری تأیید نمی‌شوند.
- همهٔ لینک‌های جدید در انتظار بررسی‌اند؛ مسیر اصلی، مسیر `/s/` و بازکردن رمز لینک همگی نظارت را رعایت می‌کنند. لینک بدون تأیید مدیر و هویت تأییدشدهٔ صاحب حساب به مقصد هدایت نمی‌شود.
- ویرایش لینک، تغییر اطلاعات پرونده و افزودن یا حذف مدرک، لینک‌های مرتبط را دوباره به صف بررسی می‌برد. تصمیم مبتنی بر نسخهٔ قدیمی پرونده یا لینک با خطای تعارض رد می‌شود.
- تعلیق حساب، نشست‌ها و لینک‌های فعال را غیرفعال می‌کند و کلیدهای API حساب هم قابل استفاده نیستند. رفع تعلیق حساب، لینک‌ها را خودکار فعال نمی‌کند.
- تأیید، رد، تعلیق و دریافت مدارک توسط مدیر در سابقهٔ نظارت ثبت می‌شود. تأیید دستی مدارک، بررسی انسانی است و اتصال به ثبت احوال یا تطبیق رسمی هویت محسوب نمی‌شود.

**اثر انتشار:** لینک‌های موجود نیز با migration جدید به وضعیت در انتظار بررسی می‌روند. کاربران قدیمی باید پرونده و تأییدهای خود را تکمیل کنند. این رفتار مطابق سیاست تأیید اجباری مدیر است.

## نگهداری خصوصی مدارک و کلیدها

مدارک JPEG، PNG و PDF، حداکثر پنج فایل برای هر حساب و پنج مگابایت برای هر فایل، پذیرفته می‌شوند. پیش از بارگذاری، ایمیل و موبایل باید تأیید شده باشند. دادهٔ فایل با AES-256-GCM و شناسهٔ پرونده/مدرک رمزنگاری و در PostgreSQL ذخیره می‌شود؛ پوشهٔ public و لینک عمومی برای مدارک وجود ندارد. مدارک فقط با نشست صاحب حساب یا مدیر، به‌شکل فایل پیوست دریافت می‌شوند و مرورگر آن‌ها را داخل سایت اجرا نمی‌کند.

نوع و امضای فایل بررسی می‌شود، اما این نسخه موتور ضدویروس یا سامانهٔ تشخیص جعل اسناد ندارد. مدیر باید فایل‌های دریافتی را در محیط بررسی امن خود باز کند. مدارک غیرضروری را درخواست نکنید؛ کاربر می‌تواند مدرک را حذف کند که باعث بررسی مجدد پرونده می‌شود. پاک‌شدن مدرک از دیتابیس به معنی پاک‌شدن آن از پشتیبان‌های قبلی نیست؛ نگهداری و دسترسی پشتیبان‌ها را جداگانه مدیریت کنید.

کلید اصلی در محیط سرور است: `DATA_ENCRYPTION_KEY`، یک کلید تصادفی ۳۲بایتی Base64. اگر این متغیر وجود نداشته باشد، از `PAYMENT_ENCRYPTION_KEY` استفاده می‌شود. در محیط عملیاتی اگر هیچ‌کدام موجود نباشد، ذخیرهٔ مدرک و کلید اتصال انجام نمی‌شود. حالت آزمایشی فقط در development فعال است.

**پیش از اولین بارگذاری، کلید ثابت را تنظیم کنید و امن پشتیبان بگیرید.** بعد از ذخیرهٔ مدارک، کلید فعال را عوض نکنید و بدون برنامهٔ انتقال کلید، متغیر `DATA_ENCRYPTION_KEY` را جایگزین کلید پرداخت قبلی نکنید؛ در غیر این صورت داده‌های قبلی خوانده نمی‌شوند. رمزهای SMTP و کلیدهای پیامک نیز با همین کلید محافظت می‌شوند.

## تنظیم ارسال از پنل مدیر

صفحهٔ `/admin/settings` یا «تنظیمات ایمیل و پیامک» در منوی مدیریت:

### ایمیل با SMTP

1. سرویس «ارسال ایمیل با SMTP» را انتخاب کنید.
2. میزبان SMTP، پورت ۵۸۷ با STARTTLS یا ۴۶۵ با TLS، نام کاربری و ایمیل فرستندهٔ تأییدشده را وارد کنید.
3. در «کلید اتصال جدید»، رمز SMTP یا رمز مخصوص برنامهٔ ارائه‌دهنده را وارد کنید.
4. تنظیمات را ذخیره و ارسال آزمایشی را با ایمیل تحت اختیار خودتان انجام دهید.

اتصال رمزنگاری‌شده اجباری است؛ گزینه‌ای برای خاموش‌کردن اعتبارسنجی گواهی وجود ندارد. وضعیت DNS فرستنده، SPF/DKIM و اجازهٔ ارسال در حساب ارائه‌دهنده باید از طرف همان سرویس تنظیم باشد.

### پیامک با کاوه‌نگار

1. در حساب پیامک خود، الگوی Verify Lookup با جایگاه `token` برای کد یک‌بارمصرف آماده و تأیید کنید.
2. سرویس کاوه‌نگار را انتخاب و نام الگو و کلید API را در پنل T4V وارد کنید.
3. ذخیره کنید و به شمارهٔ تحت اختیار خودتان پیام آزمایشی بفرستید. ارسال واقعی می‌تواند هزینهٔ حساب پیامک شما را مصرف کند.

کد موبایل شش‌رقمی، پنج دقیقه معتبر، یک‌بارمصرف و دارای حداکثر پنج تلاش اشتباه است. ارسال مجدد حداقل یک دقیقه فاصله دارد و سقف ارسال حساب مستقل از IP کنترل می‌شود. کد خام در دیتابیس ذخیره نمی‌شود. ثبت‌نام بدون تأیید، شمارهٔ شخص دیگری را برای همیشه رزرو نمی‌کند؛ یک شماره نمی‌تواند هم‌زمان در دو حساب تأیید شود.

آزمون اتصال، پذیرش پیام توسط سرویس را بررسی می‌کند؛ فقط واردکردن کد دریافتی یا مصرف لینک ایمیل، تأیید کاربر را ثبت می‌کند. تا پیش از انتخاب سرویس، کانال عملیاتی را غیرفعال نگه دارید. بدون سرویس ارسال واقعی، امکان تکمیل تأیید راه‌های ارتباطی وجود ندارد و لینک فعال نمی‌شود.

### سایر سرویس‌ها با واسط HTTPS

یک آدرس عمومی HTTPS و توکن Bearer در تنظیمات وارد کنید. سامانه یک درخواست POST با بدنهٔ JSON می‌فرستد:

```json
{
  "channel": "sms",
  "to": "+989121234567",
  "text": "متن پیام",
  "code": "123456"
}
```

برای ایمیل، فیلدهای `subject` و در پیام‌های حساب، `actionUrl` هم وجود دارند. واسط باید این قرارداد را به API سرویس انتخابی تبدیل کند و فقط پس از پذیرش پیام وضعیت موفق 2xx برگرداند. واردکردن مستقیم آدرس یک API ناسازگار کافی نیست. دنبال‌کردن redirect برای ارسال غیرفعال است تا کلید اتصال به آدرس دیگری منتقل نشود.

کلید ذخیره‌شده دوباره به مرورگر برگردانده نمی‌شود. خالی‌گذاشتن فیلد، همان کلید را حفظ می‌کند؛ هنگام تغییر نوع سرویس، کلید جدید لازم است. تنظیمات و کلیدهای واقعی را در چت نفرستید.

## انتشار روی سرور فعلی شما با سرویس‌های db و web

این بخش مخصوص همان ساختاری است که برای آن `compose.auth-repair.yml` و سرویس `auth-migrate` ایجاد شد. فایل Compose اصلی و متغیرهای موجود را با نمونه‌های نصب تازه جایگزین نکنید.

۱. نسخهٔ جدید پروژه، وابستگی‌ها و پوشهٔ کامل migrations را روی سرور قرار دهید. از دیتابیس پشتیبان بگیرید:

```bash
mkdir -p backups
docker compose exec -T db pg_dump -U t4v_admin -d t4v_production -Fc > backups/before-identity.dump
chmod 600 backups/before-identity.dump
```

اگر دستور خطا داد، ادامه ندهید. نام فایل پشتیبان موجود را بازنویسی نکنید؛ برای دفعات بعد نام تازه‌ای انتخاب کنید.

۲. پیش از اولین بارگذاری، کلید ثابت را در `.env` تنظیم کنید. برای تولید یک کلید تازه، فقط اگر هنوز کلید خصوصی فعالی ندارید:

```bash
openssl rand -base64 32
```

مقدار را خصوصی نگه دارید و به‌صورت `DATA_ENCRYPTION_KEY=...` در `.env` ثبت کنید. کلیدهای موجود برنامه و پرداخت را حفظ کنید. در `compose.auth-repair.yml`، داخل `environment` سرویس `web`، علاوه بر تنظیم اتصال موجود این خط را اضافه کنید:

```yaml
      DATA_ENCRYPTION_KEY: ${DATA_ENCRYPTION_KEY:?Set DATA_ENCRYPTION_KEY}
```

دامنهٔ عمومی `PUBLIC_SHORT_URL_BASE` هم باید `https://t4v.ir` باشد تا لینک تأیید ایمیل به دامنهٔ صحیح اشاره کند.

۳. تصویرها را بسازید، migration را با سرویس نگهداری اجرا کنید و نسخهٔ وب را جایگزین کنید. سرویس web فعلی باید هنگام اجرای migration در حال اجرا باشد، چون auth-migrate از شبکهٔ آن استفاده می‌کند:

```bash
docker compose -f docker-compose.yml -f compose.auth-repair.yml build web auth-migrate
docker compose -f docker-compose.yml -f compose.auth-repair.yml run --rm --no-deps auth-migrate
docker compose -f docker-compose.yml -f compose.auth-repair.yml up -d --no-deps --force-recreate web
curl -fsS https://t4v.ir/api/health
```

در صورت خطای هر مرحله ادامه ندهید. از `migrate reset` یا حذف volume استفاده نکنید. migrationهای جدید، پرونده‌ها و وضعیت بررسی را اضافه می‌کنند؛ حساب مدیر موجود حفظ می‌شود.

۴. وارد پنل مدیر شوید، تنظیمات ارسال را انجام دهید و با یک حساب آزمایشی این چرخه را بررسی کنید: ثبت‌نام، تأیید تماس‌ها، بارگذاری مدرک، بررسی مدرک و پرونده، ساخت لینک معلق، تأیید لینک، تعلیق و فعال‌سازی مجدد. پیش از تأیید مدیر، هیچ‌کدام از دو مسیر کوتاه لینک نباید redirect بدهند.

## محیط محلی و آزمون‌ها

در `npm run dev:local`، پیام‌های ایمیل در `.local/mailbox` و پیامک‌ها در `.local/sms` ثبت می‌شوند. این فایل‌ها حاوی لینک یا کد آزمایشی‌اند و نباید روی سرور عمومی قرار بگیرند. حالت محلی در production فعال نمی‌شود.

```bash
npm run test:identity
npm run test:notifications
npm run test:local
npm run test:admin
```

آزمون‌های یکپارچه فقط به پایگاه دادهٔ محلی و حساب‌های موقت خودشان دست می‌زنند. آزمون قرارداد SMTP و پیامک پاسخ‌های کنترل‌شده دارد و پیام واقعی به سرویس بیرونی ارسال نمی‌کند. ارسال واقعی و تحویل پیام، بعد از واردکردن مشخصات سرویس شما باید روی سرور بررسی شود.

مبنای اتصال‌ها: [مستندات SMTP](https://nodemailer.com/smtp)، [مستندات رسمی کاوه‌نگار](https://kavenegar.github.io/kavenegar_en/).
